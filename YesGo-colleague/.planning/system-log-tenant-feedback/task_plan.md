# 系统日志与租户意见反馈设计计划

## 目标

在既有多租户、领域优先和统一响应约定下，完成系统日志与租户意见反馈的可实施设计；本阶段不修改业务代码。

## 阶段

- [x] 1. 识别现有领域、入口与接口占位实现
- [x] 2. 澄清日志采集范围和反馈处理边界
- [x] 3. 基于用户微调后的数据库表，形成最终架构、API 契约、页面设计及租户系统设置迁移方案
- [x] 4. 写入、复核并提交设计文档，等待用户审阅
- [x] 5. 根据已批准设计写入并自检实施计划，等待执行方式选择

## 约束与决策

- 系统日志面向运行、诊断和溯源，不替代业务审计日志，归属 `observability`；采用 Log4j 标准日志语义，由总控配置最低记录级别。
- 意见反馈是独立的租户服务运营领域，不归属 `observability`；仅租户后台可提交，总控无提交入口，但需承担查看、处理和回复职责。
- 用户授权直接在本地 MySQL `yesgo` 创建基础表，随后会自行微调；后续实现必须以微调后的实际 DDL 为准。
- 当前已创建的 `system_event_log` 是过渡名称与过渡字段结构；用户要求最终更名为 `system_log`，并将 `level` 调整为 Log4j 级别。用户微调前不再 ALTER 该表。
- 用户随后授权直接调整数据库：已将 `system_event_log` 更名并调整为 `system_log`，新增 `system_log_issue` 承载问题处理闭环，且已初始化日志阈值配置。
- 用户决定废弃总控“集成配置”及旧的总控站点配置入口；租户系统设置以总控设置页模式承接本租户站点与品牌配置，旧 `admin-site` 管理接口由新的租户系统设置接口替代。
- 数据库采用全新库重新部署策略：不写 Django 数据迁移；`system_log`、`system_log_issue`、`tenant_feedback`、`tenant_feedback_reply` 直接维护在 MySQL 初始化脚本，并与 Django 模型同步。
- 所有租户关联数据必须后端按 `tenant_id` 隔离，ORM 关系默认不建数据库外键。
