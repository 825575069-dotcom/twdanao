## 1. 总体架构

### 1.1 架构选型：路径 B — Django 直调 QiWe

```
企业微信客户端
     ↕ (企微协议层)
QiWe 网关 (manager.qiweapi.com)
     ↕ (HTTP API + Webhook 回调)
Django 后端 (wecom + marketing_follow + tasks)
     ↕ (REST API + WebSocket)
前端 6 Tab (ai-employee-app)
```

**为什么不用 C# 中间层**：
- C# SDK 是完整的 .NET 服务，引入意味着多一个进程、多一套部署运维
- QiWe API 本质是 HTTP POST + Token 认证，Django 用 requests 库即可调用
- 单一系统单一数据库，降低复杂度

### 1.2 QiWe API 概述

- **统一端点**：`POST /qiwe/api/qw/doApi`
- **认证**：Header `X-QIWEI-TOKEN`
- **分发**：Body `method` 字段指定具体 API（共 104 个）
- **设备标识**：GUID `6803B14D-A6C9-4285-B6DD-CD791C9D2E47`
- **回调**：QiWe 向我方 Webhook URL 推送企微事件

### 1.3 三条核心数据流

| 数据流 | 触发 | 链路 |
|---|---|---|
| 被动回复 | 客户发企微消息 | Webhook → AI 生成回复 → sendText |
| 主动跟进 | 数据底座行为事件 | 事件触发 → AI 开场白 → sendText |
| 精准群发 | 用户手动创建群发任务 | 群发助手 → 逐客户 sendGroupMsg |

### 1.4 同步快返 + 异步处理

Webhook 必须在 3 秒内返回 HTTP 200（否则 QiWe 重试），但 AI 回复需要 5-10 秒。因此：
- Webhook 接收后立即返回 200
- 用 `ThreadPoolExecutor` 后台处理 AI 回复
- 消息先持久化，再异步处理

## 3. Webhook 接收与分发

### 3.1 Webhook 接口

```
POST /api/v1/wecom/webhook/
```

- 不需要 JWT 认证（外部请求），通过回调 Token 验证
- 3 秒内返回 HTTP 200
- 消息持久化后，用 ThreadPoolExecutor 异步处理

### 3.2 回调分发

| QiWe cmd | 事件类型 | 处理逻辑 |
|---|---|---|
| 15000 | 文本消息 | 存 WecomMessage → 触发 AI 回复链路 |
| 20000 | 图片消息 | 下载媒体 → 存 WecomMediaFile → 存 WecomMessage → 触发 AI |
| 11016 | 联系人变更 | 更新 WecomContact（新增/修改/删除） |
| 15500 | 设备状态变更 | 更新 WecomDevice.status（online/offline/banned）→ 被封禁时暂停所有任务 |

### 3.3 处理流程

```
QiWe 回调
  ↓
WebhookView.post()
  ├─ 验证 Token
  ├─ 解析 cmd + data
  ├─ 持久化（WecomMessage / WecomContact 更新）
  ├─ 立即返回 HTTP 200
  └─ executor.submit(process_message_async, message_id)  # 异步处理
```

## 4. AI 回复链路

### 4.1 三级开关检查

```
1. ChatSetting.ai_enabled（企业级总开关）
   ↓ True
2. WecomDevice.ai_enabled（设备级开关）
   ↓ True
3. WecomContact.ai_hosted（客户级开关）
   ↓ True
→ 进入 AI 回复流程
```

任一级别关闭，则不触发 AI，消息仅存储。

### 4.2 5 层 Prompt 注入

```
[角色定位]  ← Agent.name + Agent.description + AgentConfig.system_prompt
[知识文档]  ← knowledge_rag.py 检索租户知识库（top 3）
[数据底座]  ← data_query.py 查询客户画像 + 产品信息 + 价格
[聊天设置]  ← ChatSetting（语气/长度/称呼/禁用词/签名/工作时间）
[执行指令]  ← 场景指令（"客户发来消息，请回复"）
```

### 4.3 模仿真人回复

- **短句为主**：Prompt 指示每次回复 ≤ 30 字，可拆分为 2-3 条连续发送
- **分段发送**：多条消息间隔 1-3 秒随机
- **口语化**：指示使用口语表达，不用书面语
- **称呼**：使用客户备注名（`WecomContact.remark`）
- **无签名**：不附加任何 AI 标识或签名

### 4.4 后端校验

AI 生成回复后，后端校验：
- 不包含 `forbidden_words` 中的词
- 不包含价格承诺（"保证最低价"等）
- 不包含绝对化用语（"最好"/"唯一"等）
- 超过长度限制时自动截断或要求重新生成

### 4.5 积分扣减

回复发送后调用 `credit_service.deduct()`：
- 检查 `AgentCreditRule`（系数/免扣）
- 计算 `ceil(tokens / tokens_per_credit × coefficient)`
- 写入 `CreditLedger`（source = `wecom_chat`）
- 租户余额不足时降级为话术库匹配

### 4.6 处理流程

```
process_message_async(message_id)
  ↓
1. 三级开关检查 → 关闭则 return
2. 检查冷却期（客户最后消息后 30 分钟内不主动打扰）→ 实际是检查是否需要回复
3. 构建 5 层 Prompt
4. 调用 LLM 生成回复
5. 后端校验（禁用词/价格/长度）
6. 模仿真人分段：如内容 > 30 字，按标点拆分为多条
7. 逐条发送，间隔 1-3 秒随机
8. 发送完成后扣减积分
9. 更新 WecomContact.last_contacted_at
```

## 5. 主动跟进触发

### 5.1 双轨触发机制

| 触发方式 | 实时性 | 覆盖面 | 说明 |
|---|---|---|---|
| 事件触发 | 实时（秒级） | 依赖数据底座事件覆盖 | 数据底座行为信号 → 立即创建任务 |
| 定时兜底 | 延迟（天级） | 全量扫描 | 每天 9:30 扫描未跟进客户 |

### 5.2 支持的事件类型

| 事件 | 触发条件示例 |
|---|---|
| customer_login | 客户登录后 N 分钟内未联系 |
| product_browse | 浏览某商品 ≥ 3 次且未下单 |
| order_placed | 下单后 2 小时未跟进 |
| repeat_purchase | 30 天内复购 |
| cart_abandoned | 加购物车 24 小时未结算 |
| birthday | 生日当天/前 1 天 |

### 5.3 定时兜底

```bash
# 每天上午 9:30 执行
python manage.py run_scheduled_tasks
```

- 扫描 `trigger_type=schedule` 且 `status=active` 的 Task
- 查询符合条件的客户（如 N 天未跟进）
- 限制每日最大触发量（默认 50 人/天）
- 只在 9:00-18:00 时间窗口内发送
- 防重复：同 Task + 同客户 + 同一天只允许一条 TaskExecution

### 5.4 开场白生成

主动跟进的 Prompt 与被动回复略有不同：
- `[执行指令]` 段注入触发事件上下文（"客户王经理刚登录了系统，上次采购是阿莫西林，发一条关怀消息"）
- AI 生成的是**开场白**而非回复，语气更主动
- 同样遵循模仿真人、无签名、用备注名称呼

## 6. 精准群发

### 6.1 群发流程（4 步）

```
Step 1: 创建群发任务（选素材 + 选接收者）
Step 2: 频率校验 + 生成接收者列表
Step 3: 任务状态机（draft → pending → sending → completed）
Step 4: 逐客户发送 + 随机间隔防风控
```

### 6.2 频率校验

- 每客户每月最多 4 条群发消息（企微硬限）
- 创建任务时筛选接收者，红色标注已达上限的客户
- 跳过已达上限的客户（status = skipped）

### 6.3 防风控

- 逐客户发送（非并发批量）
- 随机间隔 2-5 秒
- 每日上限（默认 200 条/天/设备）
- 发送失败率 > 30% 时自动暂停，通知管理员

### 6.4 素材类型

| 类型 | 说明 | QiWe API |
|---|---|---|
| 文本 | 纯文字消息 | sendGroupMsg |
| 图文链接 | 标题 + 摘要 + 封面图 + 链接 | sendGroupMsg (link) |
| 小程序卡片 | 小程序名称 + 页面路径 + 封面 | sendGroupMsg (miniprogram) |

## 7. 自动任务改造

### 7.1 Task 模型扩展

在现有 `Task` 模型上新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| trigger_type | CharField | event / schedule / manual |
| trigger_config | JSONField | 事件条件或 cron 配置 |
| action_type | CharField | proactive_follow / broadcast / moments |
| action_config | JSONField | 执行动作配置 |
| status | CharField | active / paused / expired |
| valid_from / valid_until | DateTimeField | 有效期 |

一个 Task 是一条**持久规则**，可以被多次触发。

### 7.2 TaskExecution 执行记录

| 字段 | 类型 | 说明 |
|---|---|---|
| task | FK → Task | |
| tenant | FK → Tenant | |
| target_contact | FK → WecomContact | |
| status | CharField | pending → running → success / failed / skipped |
| trigger_event | JSONField | 触发时的原始事件数据 |
| result | JSONField | 执行结果 |
| started_at / completed_at | DateTimeField | |

### 7.3 事件触发器

```
数据底座行为
  ↓ (Django signals 发射)
EventDispatcher.match(event_type, tenant_id, customer_id)
  ↓ 遍历 status=active 的 Task
  ↓ 匹配 trigger_config.conditions
  ↓ 匹配成功 → 创建 TaskExecution(status=pending)
```

### 7.4 执行引擎

方案 A（推荐）：Management command + 轮询
```bash
python manage.py run_task_runner  # 每 10 秒查一次 pending 队列
```

执行流程：
```
取 status=pending 的 TaskExecution
  → 标记 running
  → 按 action_type 分发：
    ├─ proactive_follow → ProactiveFollowExecutor
    ├─ broadcast → BroadcastExecutor
    └─ moments → MomentsExecutor
  → 标记 success / failed / skipped
```

### 7.5 防骚扰护栏

| 护栏 | 逻辑 |
|---|---|
| 时间窗口 | 只在 8:00-20:00 发送，超时延到次日 |
| 频率限制 | 同一客户每天最多 1 条主动跟进，每周最多 3 条 |
| 冷却期 | 客户最后一条消息后 30 分钟内不主动打扰 |
| 月度上限 | 群发每客户每月 4 条，主动跟进每月 ≤ 8 条 |
| 全局熔断 | 当天失败率 > 30% 暂停所有任务 |

## 10. 总结与开发计划

### 10.1 设计决策总结

| # | 决策点 | 选定方案 | 理由 |
|---|---|---|---|
| 1 | 企微对接路径 | 路径 B：Django 直调 QiWe | 不引入 C# 中间层，单一系统 |
| 2 | 消息收发架构 | Webhook 快返 200 + 异步处理 | 企微要求 3 秒内响应 |
| 3 | AI 回复风格 | 模仿真人：短句/多条/口语化 | 用户要求 |
| 4 | AI 签名 | 不附加 | 用户要求 |
| 5 | 客户称呼 | 企微备注名 | 用户要求 |
| 6 | 触发机制 | 事件 + 定时兜底双轨 | 实时 + 全覆盖 |
| 7 | 执行引擎 | Management command 轮询 | 不引入 Celery |
| 8 | Prompt 注入 | 5 层 | 现有 3 层 + 聊天设置 + 执行指令 |
| 9 | 群发防风控 | 逐客户 + 随机间隔 + 月限 4 条 | 企微限制 |
| 10 | 工作流引擎 | 当前不桥接 | 保持简单 |

### 10.4 技术风险与对策

| 风险 | 对策 |
|---|---|
| QiWe 网关不稳定 | 重试 3 次 + 指数退避 + 死信队列 |
| 企微账号被封 | 监控设备状态回调，被封后暂停所有任务 |
| AI 回复质量 | 禁用词过滤 + Prompt 约束 + 后端校验 |
| 积分耗尽 | 余额预警 + 降级为话术库匹配 |
| 并发堆积 | 线程池限 20 + 队列积压告警 |
| 群发风控 | 随机间隔 + 每日上限 + 模拟人工 |
